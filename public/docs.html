Bu hujjat hech narsani "o'zingiz tushunib olasiz" deb qoldirmaydi. Har bir tushuncha nima? → nega kerak? → qanday ishlatiladi? tartibida tushuntirilgan. Agar siz Node.js va REST API bilan endi tanishayotgan bo'lsangiz — shu sahifani boshdan oxirigacha o'qing.

01Bu loyiha nima?

B2B — business to business, ya'ni korxonalar bir-biriga ulgurji savdo qiladigan tizim. Bu loyiha shunday savdo platformasining backend qismi: mahsulotlar katalogi, buyurtmalar, foydalanuvchilar va rollar bilan ishlaydigan REST API.

Loyiha o'quv maqsadida yozilgan, lekin kod haqiqiy production loyihalardagi kabi tashkil qilingan:

🧱 Modulli struktura

Har bir mavzu (products, orders...) o'z papkasida: routes → controller → service → validation.

🔐 JWT autentifikatsiya

Access token (15 daqiqa) + refresh token (7 kun), rollarga asoslangan ruxsatlar.

⚡ In-memory cache

Ma'lumotlar RAM'da saqlanadi, DB'ga yozish fonda ketadi. Redis'siz.

📋 Audit log

Har bir o'zgarish yozib boriladi, 7 kundan eskisi avtomatik o'chadi.

🛡️ Mustahkam xatoliklar

Bitta markazlashgan errorHandler, hamma xato o'zbekcha va tushunarli.

📚 Ikki xil hujjat

Interaktiv Swagger UI (/api-docs) va shu statik qo'llanma (/docs).

05Javob formati

API'ning hamma javobi bir xil ko'rinishda. Bu client tomonda kod yozishni juda osonlashtiradi: siz har doim avval success ni tekshirasiz, tamom.

✅ Muvaffaqiyatli javob (bitta obyekt)

{
  "success": true,
  "message": "Mahsulot yaratildi",
  "data": { "id": "uuid...", "title": "Noutbuk", "price": 8500000 },
  "meta": {
    "requestId": "165ca88a-...",
    "timestamp": "2026-08-19T17:53:04.450Z"
  }
}

✅ Ro'yxat (pagination bilan)

{
  "success": true,
  "data": [ { ... }, { ... } ],
  "pagination": {
    "currentPage": 1,
    "totalPages": 3,
    "totalItems": 12,
    "limit": 5,
    "hasNextPage": true,
    "hasPrevPage": false
  },
  "meta": { "requestId": "...", "timestamp": "..." }
}

❌ Xato javobi

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Kiritilgan ma'lumotlarda 1 ta xatolik bor. Quyidagi maydonlarni tekshiring",
    "details": [
      { "field": "name", "message": "Nom kamida 2 ta belgidan iborat bo'lsin", "in": "body" }
    ]
  },
  "meta": {
    "requestId": "dceeafe0-...",
    "timestamp": "...",
    "path": "/api/v1/categories",
    "method": "POST"
  }
}
meta.requestId nima uchun kerak? Bu har bir so'rovga beriladigan unikal raqam (javob header'ida ham bor: X-Request-Id). Foydalanuvchi "menda xato chiqdi" desa, shu ID ni so'raysiz va server loglaridan aynan o'sha so'rovni bir soniyada topasiz. Bu production loyihalarda hayot qutqaradigan narsa.

Client tomonda ishlatish (JavaScript)

const res  = await fetch('/api/v1/products?page=1&limit=10');
const json = await res.json();

if (!json.success) {
  // Xatoni ko'rsatamiz — message allaqachon o'zbekcha va tushunarli
  alert(json.error.message);
  return;
}

console.log(json.data);                     // mahsulotlar massivi
console.log(json.pagination.totalPages);    // umumiy sahifalar soni

06Autentifikatsiya (JWT)

Ikki xil token — nega ikkita?

Access tokenRefresh token
Yashash muddati15 daqiqa7 kun
VazifasiHar bir so'rovda yuboriladiFaqat yangi access olish uchun
Qayerda saqlanadiXotirada (RAM)Xavfsiz joyda (httpOnly cookie / secure storage)
Bekor qilish mumkinmiYo'q (muddati tugaguncha amal qiladi)Ha — bazadan o'chiriladi
Mantiq: access token o'g'irlansa ham, u atigi 15 daqiqada yaroqsiz bo'ladi. Refresh token uzoq yashaydi, lekin u bazada saqlanadi (aniqrog'i, uning SHA-256 hash'i) — shuning uchun logout qilganda uni bekor qilish mumkin. Ikkovini birlashtirsak: qulaylik + xavfsizlik.

Amaliy oqim

1. POST /auth/register  yoki  POST /auth/login
   → { accessToken, refreshToken }

2. Har bir himoyalangan so'rovda:
   Authorization: Bearer <accessToken>

3. 15 daqiqadan keyin 401 TOKEN_EXPIRED keladi:
   POST /auth/refresh  { "refreshToken": "..." }
   → yangi { accessToken, refreshToken }
   ⚠️ Eski refresh token DARHOL bekor qilinadi (rotation)

4. Chiqish:
   POST /auth/logout  { "refreshToken": "..." }
   → token bazadan bekor qilinadi

Nega "token rotation"?

Har safar /auth/refresh chaqirilganda eski refresh token bekor qilinib, yangisi beriladi. Agar o'g'ri sizning eski tokeningizni ishlatmoqchi bo'lsa — u allaqachon yaroqsiz. Bu refresh token rotation deb ataladi va OWASP tavsiya qiladigan amaliyot.

Parol xavfsizligi

  • Parol hech qachon ochiq saqlanmaydi — faqat bcrypt hash'i (10 rounds).
  • Parol talablari: kamida 8 belgi, kamida bitta katta harf, bitta kichik harf va bitta raqam.
  • PATCH /auth/change-password chaqirilsa — barcha refresh tokenlar bekor qilinadi, ya'ni barcha qurilmalardan chiqiladi. Parol o'zgargan bo'lsa, eski sessiyalar yashamasligi kerak.

Token ichida nima bor?

// accessToken payload (jwt.io da ochib ko'rishingiz mumkin)
{
  "sub":   "3d0e5c1b-...",   // foydalanuvchi ID
  "email": "admin@b2b.uz",
  "role":  "ADMIN",
  "type":  "access",         // refresh token bilan adashtirmaslik uchun
  "iat":   1755000000,       // qachon berilgan
  "exp":   1755000900,       // qachon tugaydi
  "iss":   "b2b-demo-api"    // kim bergan
}
Diqqat: JWT shifrlanmagan, faqat imzolangan. Ichidagi ma'lumotni har kim o'qiy oladi (base64 dekodlash kifoya), lekin o'zgartira olmaydi — imzo buziladi. Shuning uchun tokenga hech qachon parol yoki maxfiy ma'lumot solmang.

Kodda qanday amalga oshirilgan?

Ikki qatlamli himoya bor:

1-qatlam: route darajasida (requireRole)

// products.routes.js
router.post('/',
  writeLimiter,
  validate({ body: createProductSchema }),
  authenticate,                        // token bormi va haqiqiymi?
  requireRole('SELLER', 'ADMIN'),      // roli mos keladimi?
  controller.create
);

Bu "umumiy" tekshiruv: USER bu endpointga umuman kira olmaydi → 403 FORBIDDEN.

2-qatlam: service ichida (egalik tekshiruvi)

// products.service.js — update() ichida
if (currentUser.role !== 'ADMIN' && product.sellerId !== currentUser.id) {
  throw ApiError.forbidden("Siz faqat o'zingizning mahsulotlaringizni tahrirlashingiz mumkin");
}

Bu "aniq" tekshiruv: SELLER endpointga kira oladi, lekin boshqa sotuvchining mahsulotiga tegsa — baribir 403 oladi.

Eng ko'p uchraydigan xavfsizlik xatosi: faqat 1-qatlamni yozish. U holda har qanday SELLER boshqa SELLER'ning mahsulotini o'chira oladi. Bu Broken Object Level Authorization (OWASP API Top-10 dagi №1 muammo). Har doim ikkala qatlamni ham yozing.

Buyurtma holatlari (status) va o'tishlar

PENDING ──→ CONFIRMED ──→ SHIPPED ──→ DELIVERED   (yakuniy)
   │            │            │
   └────────────┴────────────┴──────→ CANCELLED     (yakuniy)
Hozirgi holatKeyin nima bo'lishi mumkin
PENDING — kutilmoqdaCONFIRMED, CANCELLED
CONFIRMED — tasdiqlanganSHIPPED, CANCELLED
SHIPPED — jo'natilganDELIVERED, CANCELLED
DELIVERED — yetkazilgan— (o'zgarmaydi)
CANCELLED — bekor qilingan— (o'zgarmaydi)
  • USER faqat CANCELLED qila oladi — o'z buyurtmasini bekor qilish.
  • SELLER o'z mahsuloti bor buyurtmalar holatini oldinga suradi.
  • Buyurtma bekor qilinsa — mahsulot zaxirasi (stock) avtomatik qaytariladi.
  • Noto'g'ri o'tishga urinsangiz 422 UNPROCESSABLE keladi va javobda ruxsat etilgan holatlar ro'yxati ko'rsatiladi.

09Cache mexanizmi (eng qiziq qism)

Bu loyihaning eng o'ziga xos qismi. Diqqat bilan o'qing — bu yerda tezlik va ishonchlilik o'rtasidagi kelishuv (trade-off) haqida gap boradi.

Muammo

Har bir GET /products so'rovida bazaga borish kerakmi? Baza diskda joylashgan, har bir so'rov tarmoq + disk o'qishni talab qiladi. 1000 ta foydalanuvchi bir vaqtda katalogni ochsa — baza 1000 marta bir xil ishni bajaradi. Bu isrof.

Yechim: ma'lumotni RAM'da saqlash

┌─────────────────────────────────────────────────────────┐
│  SERVER ISHGA TUSHGANDA (warm-up)                        │
│                                                          │
│  PostgreSQL ──── hammasini o'qib ────→ RAM (Map)         │
│                                        users: Map(5)     │
│                                        products: Map(12) │
│                                        orders: Map(4)    │
└─────────────────────────────────────────────────────────┘

┌─────────── O'QISH (GET) ────────────┐
│  Client → RAM'dan javob (~1 ms)     │  ← bazaga umuman bormaydi
└─────────────────────────────────────┘

┌─────────── YOZISH (POST/PATCH/DELETE) — "write-behind" ─┐
│  1. RAM'ga yozamiz            (0.1 ms)                   │
│  2. Clientga DARHOL javob     (~2 ms)  ✅                │
│  3. FONDA: navbat orqali DB'ga yozamiz                   │
│  4. DB javobidan keyin RAM'ni haqiqiy ma'lumot bilan     │
│     yangilaymiz (masalan DB qo'ygan createdAt bilan)     │
└──────────────────────────────────────────────────────────┘

Natija

Yuqorida ko'rgan POST /categories so'rovi 33 millisekundda javob berdi, holbuki DB'ga yozish keyinroq tugadi. Foydalanuvchi kutmaydi.

Xato bo'lsa nima bo'ladi? (rollback)

Bu eng muhim savol. Agar RAM'ga yozdik, clientga "muvaffaqiyat" dedik, lekin DB yozuvi yiqilsa?

syncQueue.enqueue({
  name: 'category.create',
  run: () => prisma.category.create({ data }),

  onSuccess: (saved) => cache.categories.set(saved.id, saved),  // ✅ haqiqiy ma'lumot

  onFailure: (error) => {
    cache.categories.delete(tempId);      // ❌ RAM'dan olib tashlaymiz (rollback)
    logAudit('DB_SYNC_FAILED', { error }); // audit logga yozamiz
  },
});

Bundan tashqari navbat 3 marta qayta uradi (retry) — orasida kutish vaqti oshib boradi:

1-urinish yiqildi → 500 ms kutadi
2-urinish yiqildi → 1000 ms kutadi
3-urinish yiqildi → 2000 ms kutadi
4-urinish ham yiqildi → rollback + DB_SYNC_FAILED audit log

Bu eksponensial backoff deyiladi: baza vaqtincha band bo'lsa, unga "nafas olish" vaqti beriladi.

🔄 Cache qachon yangilanadi? — uchta yo'l

Bu eng ko'p savol tug'diradigan joy. Cache — bu DB'ning nusxasi. Nusxa bo'lgan joyda doim bitta muammo bor: asl nusxa o'zgarib, nusxa eskirib qolishi. Buni ingliz tilida cache drift (cache'ning oqib ketishi) deyishadi.

Loyihada bu muammo uchta yo'l bilan yechilgan. Ular bir-birini almashtirmaydi — uchalasi bir vaqtda ishlaydi, chunki har biri boshqa turdagi holatni ushlaydi.

#Yo'lQachon ishlaydiKim ishga tushiradiKechikish

(event-driven)		 Har POST / PATCH / DELETE da Kodning o'zi 0 ms — darhol
B Qo'lda
(manual)		 ADMIN so'raganda Odam so'rov paytida
C Davriy
(scheduled job)		 Har 5 daqiqada Fon job'i maks. 5 daqiqa

A — hodisa asosida (avtomatik, darhol)

Bu asosiy yo'l. API orqali mahsulot yaratilsa — cache.products.set(...), o'zgarsa — update(...), o'chirilsa — delete(...). Kodi: src/modules/*/*.service.js. Yuqorida ko'rgan write-behind sxemasi ayni shu.

Kamchiligi: bu yo'l faqat shu server orqali o'tgan o'zgarishlarni biladi.

B — qo'lda (ADMIN tugmasi)

# 1-variant: warm-up'ni to'g'ridan-to'g'ri chaqirish.
#            Bitta resursni ham yangilay oladi.
curl -X POST http://localhost:3000/api/v1/system/cache-reload \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"resource":"products"}'   # "all" | "users" | "categories" | "orders"

# 2-variant: DAVRIY job'ning aynan o'zini "hozir ishga tushir".
#            Ya'ni "5 daqiqa kutmayman" tugmasi.

  -H "Authorization: Bearer $ADMIN_TOKEN"
Ikkalasining farqi nima?
/cache-reload — warm-up funksiyasini to'g'ridan-to'g'ri chaqiradi, bitta resursni ham yangilay oladi.
/cache-refresh-now — davriy job'ni turtadi: uning qulfi (bir vaqtda ikkita yangilanish ketmasligi) va statistika hisoblagichlari ham ishlaydi. Agar ayni damda yangilanish ketayotgan bo'lsa, javobda refreshed: false, reason: "BUSY" keladi — bu xato emas, shunchaki "hozir band" degani.

Ikkalasi ham avval syncQueue.drain(10000) chaqiradi — ya'ni navbatdagi DB yozuvlari tugashini kutadi. Aks holda hali DB'ga yetib bormagan yangi ma'lumotni eski qiymat bilan qayta yozib yuborardik.

C — davriy: har 5 daqiqada (avtomatik)

Fayl: src/jobs/cacheRefresh.job.js. Server ishga tushganda yoqiladi va setInterval orqali har CACHE_REFRESH_INTERVAL_MINUTES (default 5) daqiqada to'liq warmUpCache() bajaradi.

Nega A yetarli emas? Cache DB'dan quyidagi hollarda ajralib qoladi — va A bularning hech birini ko'rmaydi:

  1. Kimdir DB'ga to'g'ridan-to'g'ri SQL yozsa (psql, DBeaver, migratsiya skripti).
  2. Boshqa servis yoki cron shu bazaga yozsa.
  3. syncQueue 3 marta urinib ham yiqilsa va rollback qilsa — nozik holatlarda farq qolishi mumkin.
  4. Bir nechta server nusxasi ishlatilsa — biri yozadi, ikkinchisi bilmaydi.

C ana shu holatlarni har 5 daqiqada tuzatib turadi. Ya'ni eng yomon holatda ham ma'lumot 5 daqiqadan ortiq eskirmaydi.

Job'ni o'z ko'zingiz bilan ko'rish (tajriba)

  • skippedCount o'sib borsa — yangilanish intervaldan uzoqroq davom etyapti, ya'ni CACHE_REFRESH_INTERVAL_MINUTES ni oshirish yoki CACHE_WARMUP_LIMIT ni kamaytirish kerak.
  • lastDurationMs sezilarli o'ssa — jadvallar kattalashib ketgan, warm-up'ni to'liq emas, "faqat o'zgarganlarini" yuklaydigan qilish vaqti keldi.

Job kodidagi 4 ta muhim detal

  1. Hech qachon throw qilmaydi. Fon job'idagi ushlanmagan xato (unhandled rejection) butun Node jarayonini o'ldirishi mumkin. Shuning uchun job ichida hamma narsa try/catch da: DB yiqilsa xato yozib qo'yiladi, eski cache saqlanib qoladi va API ishlashda davom etadi. Eski ma'lumot — hech qanday ma'lumotdan yaxshiroq.
  2. Qulf (isRunning) bor. Agar oldingi yangilanish hali tugamagan bo'lsa (DB sekin), yangisi ishga tushmaydi — skippedCount oshadi. Aks holda sekin DB'da yangilanishlar ustma-ust tushib, holat yanada yomonlashardi.
  3. intervalHandle.unref() chaqirilgan. Bu Node'ga "shu taymer tufayli jarayonni tirik ushlab turma" deydi — aks holda Ctrl+C dan keyin ham dastur o'chmasligi mumkin.
  4. Graceful shutdown'da to'xtatiladi — server.js da stopCacheRefreshJob() chaqiriladi, shunda server o'chayotganda yarim yo'lda qolgan yangilanish bo'lmaydi.
O'chirish kerak bo'lsa: .env da CACHE_REFRESH_INTERVAL_MINUTES=0 qiling. U holda A va B yo'llari ishlashda davom etadi, faqat davriy yangilanish o'chadi. Server log'ida ogohlantirish chiqadi.
Productionda bu qanday bo'lardi? setInterval bitta jarayon uchun mukammal, lekin 3 ta nusxa (pod/instance) ishlayotganda uchalasi ham bir vaqtda DB'ni to'liq o'qiydi — bu behuda yuk. To'g'ri yechimlar:
  • Redis Pub/Sub — biri o'zgartirsa, qolganlariga xabar yuboradi. Davriy to'liq o'qish umuman kerak bo'lmaydi.
  • node-cron yoki BullMQ repeatable job — vazifani faqat bitta "yetakchi" nusxa bajaradi.
  • Kubernetes CronJob — jadval butunlay ilovadan tashqarida boshqariladi.

❓ Nega Redis emas?

Chunki bu o'quv loyihasi. Redis'ni o'rnatish, sozlash va ishga tushirish talabani asosiy mavzudan chalg'itadi. RAM'dagi oddiy Map bilan siz cache g'oyasini — invalidatsiya, warm-up, write-behind, rollback — hech qanday qo'shimcha servissiz o'rganasiz.

Retsept 2: Frontend'dan foydalanish (fetch wrapper)

const API = 'http://localhost:3000/api/v1';

let accessToken  = localStorage.getItem('accessToken');
let refreshToken = localStorage.getItem('refreshToken');

async function apiFetch(path, options = {}) {
  const res = await fetch(API + path, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(accessToken && { Authorization: `Bearer ${accessToken}` }),
      ...options.headers,
    },
  });

  const json = await res.json();

  // Token muddati tugagan bo'lsa — yangilab, so'rovni QAYTA yuboramiz
  if (json.error?.code === 'TOKEN_EXPIRED' && refreshToken) {
    const ok = await yangilash();
    if (ok) return apiFetch(path, options);
  }

  if (!json.success) throw new Error(json.error.message);
  return json;
}

async function yangilash() {
  const res  = await fetch(`${API}/auth/refresh`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ refreshToken }),
  });
  const json = await res.json();
  if (!json.success) { chiqish(); return false; }

  accessToken  = json.data.tokens.accessToken;
  refreshToken = json.data.tokens.refreshToken;
  localStorage.setItem('accessToken', accessToken);
  localStorage.setItem('refreshToken', refreshToken);
  return true;
}

function chiqish() {
  accessToken = refreshToken = null;
  localStorage.clear();
  location.href = '/login';
}

// Ishlatish:
const { data, pagination } = await apiFetch('/products?page=1&limit=10');

cp .env.example .env
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"  # kalit yasash

❌ @prisma/client did not initialize yet

npx prisma generate

schema.prisma ni o'zgartirgandan keyin bu buyruqni har doim bajaring.

❌ 401 kelyapti, token esa bor

  • Header formati to'g'rimi? Authorization: Bearer <token> — Bearer so'zi va bitta bo'sh joy shart.
  • Token 15 daqiqada eskiradi → /auth/refresh chaqiring.
  • Swagger'da: Authorize oynasiga faqat tokenning o'zini qo'ying, Bearer yozmang.
  • .env dagi JWT_ACCESS_SECRET o'zgargan bo'lsa — eski tokenlar yaroqsiz bo'ladi.

❌ 429 Too Many Requests

Limitga yetdingiz. Bir daqiqa kuting yoki dasturlash vaqtida .env da oshiring:

RATE_LIMIT_MAX=1000
AUTH_RATE_LIMIT_MAX=100

❌ Ma'lumot yaratdim, lekin bazada yo'q

Cache write-behind ishlatadi — DB yozuvi bir necha millisekund keyin bo'ladi. Tekshiring:

curl $BASE/system/health -s | grep -o '"syncQueue":{[^}]*}'
curl $BASE/audit-logs?action=DB_SYNC_FAILED -H "Authorization: Bearer $ADMIN"

Agar DB_SYNC_FAILED yozuvi bo'lsa — DB yozuvi 3 marta urinib ham yiqilgan va cache rollback qilingan.

❌ Swagger UI ochilmayapti / bo'sh

  • Brauzer konsolini oching — CSP xatosi bormi? app.js da contentSecurityPolicy: false bo'lishi kerak.
  • To'g'ridan-to'g'ri JSON'ni tekshiring: /api-docs.json
